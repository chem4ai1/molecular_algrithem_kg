# 12 · 溯源回原文：实测效果与新节点抽取位置

## 12.1 现有溯源能到什么粒度

| 机制 | 位置 | 给出什么 |
|---|---|---|
| `provenance.trace` | `semantic/provenance.py` | 关联 Paper、抽取报告命中阶段、表格单元格（model/metric/value/provenance） |
| `relation_index.json` | `storage/sciforge/provenance/` | 节点↔论文索引（2405 节点 / 788 论文） |
| `model_results[].provenance` | 抽取报告 | `table_extract:N`（表序号，但**与 md 的 Table N 不对应**） |

**缺口**：以上都不给「原文第几行」。新增 `semantic/source_locator.py` 补这一层。

## 12.2 定位设计与等级

md 里表格已被拆成「每行一个单元格」，结构丢失，所以定位分三级：

| 等级 | 判据 |
|---|---|
| high | 表块 + 模型名行 + 表头指标序数，且值完全一致 |
| medium | 同块内值一致，但指标位次对不上（竖排表 / 多级表头） |
| low | 仅按标签全文匹配（非数值节点） |

不做的事：**不猜行列坐标**。结构缺失时宁可给 medium，也不假装精确。

```bash
python stages/2_semantic_layer/trace_to_source.py --node benchmark:zinc
python stages/2_semantic_layer/trace_to_source.py --paper 2411.06608
```

## 12.3 实测效果（4 篇样例）

| 论文 | 基准 | 单元格 | high | medium | 定位率 | 未定位但在原文 | 原文根本没有 |
|---|---|---|---|---|---|---|---|
| 2411.06608 | 6 | 290 | 118 | 18 | **46.9%** | 19 | 135 |
| 2611.06237 | 21 | 97 | 0 | 27 | 27.8% | 27 | 13 |
| 2405.03370 | 3 | 3 | 0 | 0 | 0% | 0 | 0 |
| 2302.09048 | 1 | 127 | 0 | 0 | 0% | 66 | 61 |

### 三个结论

1. **横排表能精确定位**：`benchmark:zinc` 的 15 个单元格全部 high，
   MolMiner L424-428、HierVAE L430-434、GDSS L436-440，与原文逐行一致。
2. **竖排表只能到 medium**：Table S1（属性作行）能靠值匹配到块内，但给不出指标位次。
3. **46.6% 的值在原文根本不存在**（2411 的 135/290）—— 这不是定位器的问题，
   是抽取错位：`model="Validity↑"`、`metric="Dataset"` 这类把表头当模型名的行。

## 12.4 新节点应该在哪抽

判断原则：**节点由它描述的那段原文所在阶段产出**，不由谁需要它决定。

### Contribution 指向 E1（Paper 核心）

| 项 | 内容 |
|---|---|
| 原文位置 | 引言末尾的 contributions 列表 / 摘要第二句 / 结论首段 |
| 信号词 | we propose / we introduce / our contribution / unlike prior work / to the best of our knowledge |
| 为什么在 E1 | 贡献是论文级声明，与 research_question 同源；E1 已读摘要与引言 |
| 不能放哪 | 不能放 E2（只读方法节，拿不到「为什么新」）；不能放 E6（只读谱系） |
| 溯源字段 | contribution.evidence（逐字句）+ section + char_span |

### ExperimentArm 指向 E3 + E4

| 项 | 内容 |
|---|---|
| 原文位置 | 实验设置节（"Experimental Setup" / "Baselines" / "Ablation"）+ 结果表的列/行标题 |
| 信号词 | we compare against / baselines / we ablate / w/o / our variant / we sweep / grid search |
| 为什么拆两段 | E3 读设置（有哪些组、什么配置），E4 读数值（哪一行属于哪个组） |
| 不能放哪 | 不能只放 E4：数值行里看不出「这是 baseline 还是消融」；也不能只放 E3：没有数值就无法落到具体行 |
| 溯源字段 | arm.evidence（设置节原句）+ model_results[].arm（组 id）+ table_ref |

### Assumption 指向 E2（算法与模块）

| 项 | 内容 |
|---|---|
| 原文位置 | 方法节的假设声明 / 限制章节 / 定理前提 |
| 信号词 | assume / assumption / we rely on / holds when / provided that / under the condition |
| 为什么在 E2 | 假设是方法成立的前提，属方法描述；E2 已读机制与模块 |
| 不能放哪 | 不能放 E1（E1 只看论文级问题）；不能放 E6（E6 只写继承关系） |
| 溯源字段 | assumption.evidence（逐字句）+ applies_to（Algorithm 或 Module） |

## 12.5 用溯源验收抽取（这是本次最大的收获）

定位器不只是「看原文」，它同时是一个**抽取质量验收器**：

```
值能在原文找到 且 能定位到行 → 抽取可信
值能在原文找到 但 定位失败     → 定位算法待改进（不是抽取的错）
值在原文根本不存在             → 抽取可疑（表头错位 / 解析丢表 / 编造）
```

2411.06608 实测：290 个单元格里 **135 个（46.6%）的值在原文中不存在**。
抽查发现是同一类错误：

```
model = "Validity↑"   metric = "Dataset"   value = "95.81"   ← 表头被当成模型名
model = "√"           metric = "Strategy"  value = "1.2779"
```

这类错误在只有图、没有原文对照时看不出来，加上定位器就无处可藏。

建议把 `locate_rate` 与 `value_not_in_text` 作为 E4 的**质量指标**写进抽取报告。

## 12.6 实施顺序

| 步 | 做什么 | 依赖 | 可验证 |
|---|---|---|---|
| 1 | 把 `trace_to_source.py` 接进抽取收尾，每篇出定位率 | 无 | 4 篇跑通 |
| 2 | E4 修表头错位（模型名/指标名互换、纯符号当模型名） | 步 1 的 value_not_in_text 指标 | 2411 的 135 降到 <30 |
| 3 | E1 加 contribution 抽取（含 evidence 逐字句） | 无 | 定位能回到引言那几句 |
| 4 | E3+E4 加 experiment_arm | 步 3（contribution 需被 arm 引用） | 矩阵四类能逐组清点 |
| 5 | E2 加 assumption | 无 | 定位能回到方法节假设句 |
| 6 | 定位器支持竖排表（属性作行） | 步 1 | 2611 的 medium 转 high |

**先修 E4 再加新节点**：当前 46.6% 的数值回不到原文，
在这个基础上加 Contribution/ExperimentArm，只会把错误传导到新节点上。

## 12.7 边界

- 定位是**行级**，不是字符级：表格结构已被拆散，给不出「第几行第几列」。
- `table_extract:N` 与 md 的 `Table N` **不对应**，只能靠三元组搜索兜底。
- 2302.09048 定位率 0%，原因是表格为竖排 + 多级表头，不是值不存在（66 个值在原文）。
- 定位器不判断「这个数对不对」，只回答「这个数在原文哪一行」。
