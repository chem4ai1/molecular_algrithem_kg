# 05 · 实验设计必须满足什么惯例

第五个必须回答的问题：**这个实验设计，审稿人会认吗？**

## 5.1 强制实验矩阵（四类缺一不可）

| 项 | 最低要求 | 为什么 |
|---|---|---|
| 主实验 | ≥1 个验证核心假设的实验 | 没有主实验，论文没有主张 |
| baseline | **≥3**：SOTA 复现 + 经典方法 + naive（随机/多数类/恒等） | 只有 SOTA 会显得挑对手；naive 是最低门槛 |
| 消融 | 逐创新组件 leave-one-out，**≥2 组** | 证明「涨点来自你声称的组件」 |
| 超参 | ≥1 个核心超参 × **≥3 个值点** | 证明不是精心调出来的单点 |

缺项不是「可以后面补」，而是这个实验设计**不成立**。

## 5.2 为什么 baseline 要三个

- **SOTA 复现**：证明你比当前最好更好（自己复现，不用论文里的数）
- **经典方法**：证明你不是只赢了一个弱对手
- **naive**：随机/多数类/恒等 —— 如果赢不了 naive，说明任务本身有问题

只报「我们比 SOTA 好」的论文，审稿人第一个问题是：你的 SOTA baseline 是在什么设置下跑出来的？

## 5.3 消融的正确做法

1. 从方法注册表里**枚举创新组件**（不是把所有模块都算）
2. 逐个 leave-one-out（去掉 / 换成旧版本）
3. 每个消融跑完整实验（不是只跑一次）
4. 判定规则：**新的必须严格优于旧的**，打平要 refine，不能算通过

常见错误：把「去掉整个模块」当成消融，实际上应该拆到组件级
（如「去掉注意力」和「去掉注意力的位置编码」是两件事）。

## 5.4 seed 策略

| 场景 | 最低 seed 数 | 说明 |
|---|---|---|
| 主结果 | 3（lite ≥2） | 必须报 mean±std |
| 消融 | 2 | 至少证明方向一致 |
| 超参扫描 | 1 | 可接受，但要说明 |

单 seed 的结果只能写 "we observe"，不能写 "improves"。

## 5.5 阶梯：先复现 baseline，再跑候选

顺序不能反：

1. 在子集上**复现 baseline**（确认你的 pipeline 能跑出原文量级）
2. 在子集上跑候选 → 三态判定（GOOD 增益 >0.15% / ENGINEER 打平 ≤2 轮 / BAD 丢弃）
3. 只有「严格优于你复现出来的 baseline」才升到全量

> ties 不算赢。子集上打平就升 full，是「子集侥幸」变成「论文结论」的典型路径。
