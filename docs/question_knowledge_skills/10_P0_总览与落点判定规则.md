# P0 · 总览：阶段划分、落点判定规则与语义层实测基线

> 本目录（`docs/question_knowledge_skills/`）原有 8 份 `00–07` 文档回答的是「**要改什么 prompt、补什么字段**」。

>
> 全部落点以两处真实资产为准，不假设上游仓库口径：
> - **语义层 v4.1**：`src/capfactory/semantic/tbox_v4.py`（6 类 / 9 关系）+ A-Box `storage_cf/sciforge/batch10_semantic_v4.json`（6001 节点 / 7460 断言）+ 向量 `storage_cf/semantic/vector/nodes_meta.json`（6001 × dim 1024，`bge-m3`）
> - **应用层 / 运行时**：`src/capfactory/applayer/tbox.py`（8 类 / 9 关系）、`src/capfactory/paperapp/tbox.py`（14 动态类 + 26 阶段 + 14 ChoicePoint）、`src/capfactory/reprospec/`、`src/capfactory/sciforge/contracts.py`

## P0.1 为什么阶段要按 26 节点切，而不是按「写作流程」切

`docs/skills/APPLICATION_ONTOLOGY_FRAMEWORK.md` 已确认：论文生成的真实编排是 26 节点 DAG（`orchestrator/auto-pipeline`），
且 `paperapp` 已把这 26 阶段与 14 个 ChoicePoint 落成代码（`paperapp/tbox.py::CHOICEPOINTS`）。
按「引言 / 方法 / 实验 / 结论」切阶段会把**决策点**切散——真正卡住流程的是门（gate），不是章节。

## P0.2 落点判定规则：一个问题只能落在四类之一

这是本批最重要的约定。**不要看到问题就新建类**——语义层冻结在 6 类是有原因的（`tbox_v4.py` 注释：只保留客观可抽取的事实）。

| 落点 | 判据 | 写入位置 | 例子 |
|---|---|---|---|
| **A · 已有属性**（最优先） | 现有 6 类的某个字段语义够用，只是**内容质量**不够 | 不改 schema，只改抽取 prompt / 校验 | `Paper.research_question` 已有 → 问题锚定先复用，而不是新建 `ProblemAnchor` |
| **B · 新增属性** | 一句话能说清、**不跨论文聚合、不需要独立查询** | `tbox_v4.SEMANTIC_CLASSES` + `extraction/contracts.py` + `validator.py` | `Benchmark.protocol`（seeds/split/epochs）、`AlgorithmModule.is_novel_component` |
| **C · 新增关系 / 边属性** | 是**两个既有节点之间**的东西 | `tbox_v4.SEMANTIC_RELATIONS` 或 `assertions[].properties` | `SUBCLASS_OF.properties.assumption_delta`、`RELATED_TO.properties.verified` |
| **D · 新增类**（最后手段） | 需要独立 id、被多篇论文复用、要单独查询/聚合 | 语义层（需版本升 v4.2）或**应用层 8 类扩容 / paperapp 14 动态类** | 引用实体 `Citation`、消融组 `AblationGroup`、实验节点 `ExperimentRun` |

**默认层级偏好**：`A > B > C > D`，且 `D` **优先落在应用层/paperapp，不落在语义层**。
理由：语义层一动，`spec_hash` / `method_sau_hash` / 5 套已跑产物全部失效（`05_语义层与本体治理.md` §5.5 硬约束），
而应用层 `app_generation.json` 本来就是可增量重算的。

> 本批表格里每行都标了 `落点` 列的 `A/B/C/D`，并在 `B`/`C`/`D` 行注明「是否进 `stable_key()`」——**一律不进**。

## P0.3 语义层实测基线（这决定了哪些问题是真缺口）

以下是对 `batch10_semantic_v4.json` 的实测统计，**不是估计**。凡是覆盖率为 100% 的属性，问题就只是「抽取质量」；覆盖率低的，才是「结构缺口」。

### P0.3.1 节点与断言

| 类型 | 节点数 | 断言（关系）数 |
|---|---:|---|
| `AlgorithmModule` | 2856 | — |
| `Algorithm` | 1674 | — |
| `Paper` | 808 | — |
| `Benchmark` | 604 | — |
| `CodeFunction` | 49 | — |
| `CodeRepository` | 10 | — |
| **合计** | **6001** | **7460** |

关系分布：`HAS_MODULE 2862` / `PROPOSES_METHOD 1666` / `SUBCLASS_OF 1083` / `EVALUATED_ON 984` / `MODULE_IMPLEMENTED_BY 758` / `HAS_FUNCTION 49` / `RELATED_TO 48` / `HAS_CODE 10`。

**三个必须记住的实测事实**：

1. `assertions[].attribution` **100% 是 `analyst_synthesis`**，`evidence_ids` **100% 为空数组**。
   → 所有关系的证据都在 `assertions[].properties.evidence` 的**逐字串**里，但**没有指向 Paper 内位置的指针**。
   这直接决定了 P3 阶段「引用上下文校验」和 P1 阶段「gap 支撑」都缺同一块地基。
2. `AlgorithmModule` 的 id **100% 带 arxiv 号**（`algorithmstep:<arxiv>:<序号>:<slug>`），但 `Probability` 只有 36/808 篇 Paper 有 `flow_family`。
   → 「模块归属哪篇论文」只能靠 id 解析，**没有显式关系边**；跨论文模块复用率为 0（这是设计使然，见 `normalize_for_repro()` 的跨论文剔除）。
3. `Benchmark.model_results` 只有 **152/604** 个基准有（12835 条结果），`metrics` 有 **429/604**（811 条，其中 772 条有 `direction`）。
   → 数值层是**稀疏**的：P3「claim 保真度」在 3/4 的基准上无法用现有结构算出来。

### P0.3.2 属性覆盖率（B 类落点的可行性依据）

| 类 | 属性 | 覆盖率 | 结论 |
|---|---|---:|---|
| `Paper` | `title / arxiv_id / research_question / domain / why_hard / keywords / relation_hints` | 1.00 | 问题锚定**可复用** `research_question`（A 类），只需补 hash 与回引校验 |
| `Paper` | `problem_category` / `domain_code` | 0.97 | 领域分类够用；`evidence_norm` 是真空缺（B 类新增） |
| `Paper` | `doi` / `year` | 0.002 | 引用权威**结构性缺失**（C/D 类） |
| `Paper` | `flow_family` | 0.04 | 科技树切片**几乎不可用** |
| `Algorithm` | `name` | 1.00 | — |
| `Algorithm` | `mechanism / task_type / problems_solved / why_it_works / applicable_to` | 0.44–0.46 | 一半算法是「被引用实体」而非「被抽取方法」，这是正常的 |
| `Algorithm` | `origin / paper_id` | 0.54 | 可用于「是否本文提出」判定 |
| `Algorithm` | `limitations` | 0.27 | 局限文本稀疏 → `Limitation` 应用层节点只能覆盖 1/4 |
| `AlgorithmModule` | `name / mechanism / formula / inputs / outputs` | 1.00 | **全部满**，所以「模块级」问题都不是抽取缺口，而是**新增语义标记**（B 类） |
| `Benchmark` | `name / input_form / output_form / modality / research_object` | 1.00 | 数据契约满 → `DataContract` 可全量派生 |
| `Benchmark` | `metrics` | 0.78 | — |
| `Benchmark` | `n_samples` / `scale` | 0.51 / 0.48 | 规模证据**一半缺失** → P3「数据规模匹配」只能部分判定 |
| `Benchmark` | `model_results` | 0.34 | 数值证据**最薄弱** |
| `Benchmark` | `sota_by_metric` | 0.14 | 动态 SOTA 基本靠 `is_sota` 标记 |
| `CodeRepository` | `repo_name / local_path / is_original_repo` | 1.00 | 只有 10 个仓库 → 代码层证据极稀 |
| `CodeFunction` | 全字段 | 1.00 | 只有 49 个函数 → `MODULE_IMPLEMENTED_BY` 只覆盖 758 条（占模块 27%） |

**由此得出本批的核心判断**：

- 「模块级、基准级」的知识点 → **绝大多数是 B 类（加属性）**，不是 D 类（加类）。
- 「引用、实验运行、消融组」的知识点 → **D 类，且必须落应用层**（语义层不承接）。
- 「证据定位」的知识点 → **C 类（边属性）**，且必须先补 `assertions[].properties` 的 `char_span`，否则 P3 整段判不了。

## P0.5 表结构说明（每份文件统一）

每份阶段文件里的主表固定 9 列，含义如下：

| 列 | 含义 |
|---|---|
| `#` | `DK-<阶段>-<序号>` |
| **决策 / 问题** | 这个阶段真正会卡住你的一句话，必须是**能被判错**的陈述 |
| **触发信号** | 什么时候你会意识到「这个问题出现了」——来自真实产物字段，不是猜 |
| **不做会怎样** | 具体后果（哪条结论会错、哪个门会假通过） |
| **知识点** | `KP-xxx` 编号 + 名字 |
| **落点层级** | `A / B / C / D`（见 P0.2） |
| **语义层挂载** | 具体到 `类.属性` 或 `关系.properties`；D 类写「应用层：`类名`」 |
| **判据 / 阈值** | 能写成代码的判定条件；写不出就说明这个知识点还没想清楚 |
| **首次生效阶段** | 该知识点最早在哪一步被用上（用于排期与缓存 key） |

表后固定三节：

1. **本节小结**：该阶段最容易被忽略的 2–3 条（不重复表格内容）
2. **与既有文档的关系**：指回 `00–07`、`docs/skills/`、`docs/plan/`
3. **反模式**：该阶段「看起来对但会出事」的做法

## P0.7 一句话总纲

**这套语义层已经把「论文说了什么」抽得很满（模块属性 100%、基准契约 100%），缺的全部是「凭什么这么说」——证据指针、实验条件、权威引用、人类决定。**
所以各阶段的问题清单会有同一个形状：**前半段缺的是可判定性，后半段缺的是可追溯性。**
