# P2 · 阶段 5–6c：方法预注册与实验执行

> 覆盖 26 节点：`5` method-registry（8 节 + §3 hash lock，**人工审批**）→ `6` verification-routing → `6a` theory-derivation → `6b` dynamic-sandbox（toy）→ `6c` experiment-execution（full + 后台）。
>
> 语义层现状（实测）：`AlgorithmModule` 的 5 个属性**覆盖率 100%**，但**没有任何一个是「这是不是创新组件」**；
> `Benchmark.n_samples` 只有 51%、`scale` 48%、`model_results` 34%；
> `assertions[].properties.evidence` 是逐字串但无位置指针。
> 也就是说：**这一阶段缺的不是「方法描述」，而是「方法的承诺」——做哪些实验才允许说这句话。**

## P2.2 本节小结（表外三件事）

1. **`AlgorithmModule` 的五个属性全满，反而是个陷阱。**
   因为它让人觉得「模块信息已经够了」。
   实际上 `mechanism / inputs / outputs / formula` 描述的是**模块是什么**，
   而消融需要的是**模块有多重要**——这是两个正交维度。
   `is_novel_component` 是唯一需要新增的字段（B 类），且**必须允许显式 `false`**，否则会诱导 LLM 全标 true。

2. **实验矩阵必须是「锁的一部分」，不能是「建议」。**
   `method-registry` 的 Section 3 hash lock 之所以有效，是因为**看到结果后改不了**。
   如果 `experiment_matrix` 存在 `METHOD_REGISTRY.md`（散文）而不是锁文件里，它就不是预注册。
   → 落点必须写进 `METHOD_LOCK` 的 hash 计算范围，且 `missing → BLOCKED` 而不是 `WARN`。

3. **`protocol` 是整条链最便宜的一次投资。**
   它一个字段（`seeds / split / eval_script / epochs / hardware`）同时喂饱四处：
   DK-P2-04（公平比较）、DK-P2-05（保真度）、DK-P2-14（敏感性）、DK-P2-15（规模匹配）。
   这就是为什么 `03_prompt改造对照表.md` 把它列为 P0。

## P2.4 反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 为通过 `experiment_matrix` 把 baseline 数量填够但不写来源 | 数字凑齐了，公平性没解决 | 每个 baseline 必须能解析到 `Benchmark.model_results` 的实值或 `SourcePaper` |
| toy FAIL 时「调小 min_gain 让它 PASS」 | 阈值被优化，门失效 | `min_gain` 写进 `config.yaml` 并被测试锁定；变更需 `HumanDecision` |
| 让 `is_novel_component` 默认 true | 消融组爆炸，且掩盖真正创新点 | 默认 `false`，只标论文明确声称的 |
| 把 `protocol` 缺失当错误直接拒绝 | 诱导 LLM 编造 split（"80/10/10"） | 缺失是合法 `null`，只降保真度、不阻塞 |
| 用 `MODULE_IMPLEMENTED_BY` 存在 = 模块已实现 | 27% 覆盖率下会造成大量假阴性/假阳性 | 必须看 `align_score`，无函数标 `absent` |
